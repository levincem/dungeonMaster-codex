## Short Version

At this point, the extracted original tables should be treated as the trusted source. When the current runtime still differs from them, that difference should be read as an integration gap, not as a lack of source data.

There are two different layers in the current data pipeline:

- [public/dungeon.json](D:\DungeonMaster-codex\public\dungeon.json)
  - extracted from original `DUNGEON.DAT`
  - strong source for maps, placed objects, texts, sensors, creatures, and raw object payloads

- [public/game_db.json](D:\DungeonMaster-codex\public\game_db.json)
  - derived gameplay/reference database generated by hardcoded tables in
    [assets/OriginalDataExtraction/parse_full.js](D:\DungeonMaster-codex\assets\OriginalDataExtraction\parse_full.js)
  - useful for remake gameplay
  - not itself a byte-perfect extraction of original runtime stat tables

We now also have a third, much stronger source:

- [assets/OriginalDataExtraction/output/atari_i559_stats.json](D:\DungeonMaster-codex\assets\OriginalDataExtraction\output\atari_i559_stats.json)
  - decoded from the original Atari ST [GRAPHICS.DAT](D:\DungeonMaster-codex\assets\OriginalDataExtraction\OriginalAtariGame\HardDisk\2009-02-22%20PP\GRAPHICS.DAT)
  - extracted from `0559.RAW1` using the Atari ST v1.1 `.map`
  - currently the best proven source for original balance tables

And now a fourth source for attacks/spells:

- [assets/OriginalDataExtraction/output/atari_i560_stats.json](D:\DungeonMaster-codex\assets\OriginalDataExtraction\output\atari_i560_stats.json)
  - decoded from the original Atari ST `0560.RAW1`
  - canonical source for attack tables, legal attack sets, and spell descriptors

And now a fifth source for runtime helper tables:

- [assets/OriginalDataExtraction/output/atari_i562_stats.json](D:\DungeonMaster-codex\assets\OriginalDataExtraction\output\atari_i562_stats.json)
  - decoded from the original Atari ST `0562.RAW1`
  - canonical source for drop order, carry-location masks, icon-display anchors, sound table entries, palette tables, and related runtime helper arrays

And a sixth source for UI/input tables:

- [assets/OriginalDataExtraction/output/atari_i561_stats.json](D:\DungeonMaster-codex\assets\OriginalDataExtraction\output\atari_i561_stats.json)
  - decoded from the original Atari ST `0561.RAW1`
  - canonical source for button hitboxes, key-translation groups, movement button rectangles, drop areas, and related UI helper tables

## What Is Directly Extracted

From [assets/OriginalDataExtraction/parse_full.js](D:\DungeonMaster-codex\assets\OriginalDataExtraction\parse_full.js):

- map geometry and offsets
- tile bytes and tile types
- raw door / teleporter / text / sensor / creature / weapon / armor / scroll / potion / container / misc entries
- object payload fields such as:
  - weapon type, charges, flags
  - armor type, flags
  - potion type, power
  - misc type, charge count
  - creature type, count, raw hp values, direction

These raw payloads end up in [public/dungeon.json](D:\DungeonMaster-codex\public\dungeon.json) and are the strongest “original-file” source we currently have.

## What Is Still Derived

In [assets/OriginalDataExtraction/parse_full.js](D:\DungeonMaster-codex\assets\OriginalDataExtraction\parse_full.js), the `GAME_DB` section is explicitly hardcoded.

Examples:
- `creatureTypes`
- `weaponTypes`
- `armorTypes`
- `potionTypes`
- `miscTypes`

The file itself labels this as:

- `source: "Derived gameplay/reference database used by the remake"`
- `note: "Not a byte-perfect export of GRAPHICS.DAT tables..."`

So values such as:
- base HP
- armor values
- hit probability
- attack speed
- move speed
- experience
- weapon damage ranges
- item weight

should currently be treated as:

- useful remake reference data
- partially validated
- not yet proven as direct extraction from the original data files

Current match coverage:

- monsters: `25 / 27`
- weapons: `20 / 46`
- clothing: `18 / 58`
- misc: `15 / 53`
- foods with current nutrition values: `5 / 8`

Important nuance:

- the monster alignment is already very good once source-name aliases are applied
  - for example `FlyingEye -> Wizard Eye`
  - `AntMan -> Trolin`
  - `DethKnight -> Animated Armour`
- the weapon / clothing / misc coverage is much lower because `game_db.json` only models a gameplay-useful subset, not the full original table space
- this means the remake is no longer “blind” on index identity, but it is still incomplete on exact per-entry numeric balance values

## What The Original Source Code Now Confirms

The source code also confirms the original runtime table layout, even if we have not yet extracted every byte-perfect numeric value from the shipped PC data:

- `MonsterDescriptor[27]`
- `FoodValue[8]`
- `Byte8946[54]` for misc weights
- `ClothingDesc[58]`
- `weapons[46]`
- `ObjDesc[180]`

So we now know:

- the exact table counts
- the canonical original enum ordering
- the field structure used by the engine

That direct recovery is now achieved for the canonical Atari DM1 stat payload through `0559.RAW1`.

It is also achieved for the original attack/spell payload through `0560.RAW1`.

It is also achieved for the original runtime helper block through `0562.RAW1`, with one important nuance:

- the named proven structure consumes `1818` bytes
- the Atari file is `1826` bytes long
- the remaining `8` bytes are preserved as raw trailing data instead of being guessed at

What remains open is mostly:

- mapping every raw numeric field to a polished remake-facing label
- reconciling current `game_db.json` values against the newly extracted Atari truth
- deciding which derived convenience fields should stay derived and which should now be generated from the canonical payload

Important nuance:

- original melee damage is not a single per-weapon stat
- the engine combines:
  - weapon descriptor data from `0559`
  - weapon `attackClass` from `ObjDesc`
  - legal attacks from `0560`
  - per-attack values from `0560`
  - runtime formulas in [Attack.cpp](D:\DungeonMaster-codex\assets\OriginalDataExtraction\sourceCode\Dungeon_Master_FTL_Games_1987_Source_Code\csb\CSBwin_SRC_20190702\src\Attack.cpp)

So current remake `weapon.damage` ranges are still an interpretation layer, not a byte-perfect original field.
