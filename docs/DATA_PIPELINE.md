# Data Pipeline

Current data pipeline status as of `2026-04-11`.

## Canonical flow

There are now two distinct roles:

- extraction output / proof data
- runtime input data

### Extraction output

The extraction scripts under [assets/OriginalDataExtraction](/D:/DungeonMaster-codex/assets/OriginalDataExtraction) write their generated reference outputs to:

- [assets/OriginalDataExtraction/output](/D:/DungeonMaster-codex/assets/OriginalDataExtraction/output)

This directory is the working area for:

- reverse-engineering outputs
- audits
- comparisons
- generated reference artifacts

### Extraction reference exports

Longer-lived reference JSON exports that are not part of the runtime package are now kept under:

- [assets/OriginalDataExtraction/reference_exports](/D:/DungeonMaster-codex/assets/OriginalDataExtraction/reference_exports)

This keeps `public/` focused on browser assets and the small set of extraction inputs that are still truly needed there.

### Runtime canonical data

The runtime canonical copies used by the app live in:

- [src/assets/data](/D:/DungeonMaster-codex/src/assets/data)

For the main parser outputs, this now includes at least:

- [src/assets/data/dungeon.json](/D:/DungeonMaster-codex/src/assets/data/dungeon.json)
- [src/assets/data/game_db.json](/D:/DungeonMaster-codex/src/assets/data/game_db.json)

Important distinction:

- `assets/OriginalDataExtraction/output/dungeon.json` is the full extraction/audit dump
- `assets/OriginalDataExtraction/output/runtime_dungeon.json` is the compact runtime-oriented snapshot
- `src/assets/data/dungeon.json` is the canonical runtime copy of that compact snapshot

These files are generated by:

- [assets/OriginalDataExtraction/parse_full.cjs](/D:/DungeonMaster-codex/assets/OriginalDataExtraction/parse_full.cjs)
- [assets/OriginalDataExtraction/parse_full.js](/D:/DungeonMaster-codex/assets/OriginalDataExtraction/parse_full.js)

`parse_full` now acts as the runtime packaging entry point:

- it generates the full `dungeon.json`
- it derives `runtime_dungeon.json` as a compact snapshot for the app
- it generates `game_db.json`
- it runs the mechanisms export and keeps `mechanisms.json` as a generated reference artifact
- it syncs extraction-side reference artifacts still needed by audit scripts into `assets/OriginalDataExtraction/output/`
- it syncs only the runtime reference JSON files still actually consumed by the app into `src/assets/data/`
- it syncs extraction-linked support assets still actually consumed by the app into `src/assets/`
- it writes a packaging manifest to `output/runtime_data_manifest.json` and `src/assets/data/runtime_data_manifest.json`

## What changed

Previously, `parse_full` also wrote `dungeon.json` and `game_db.json` into `public/`.

That duplication was no longer aligned with the runtime architecture, because the actual app now reads its canonical boot data from `src/assets/data/`.

So the parser has been realigned to:

- keep `output/` for extraction and proof artifacts
- write runtime copies to `src/assets/data/`
- stop treating `public/` as the canonical home for these two runtime datasets
- copy a small number of still-needed reference exports from `public/` into `output/` so audit scripts can stop depending on `public/` directly
- prefer `reference_exports/` over `public/` for extraction-side reference JSON when available

For auxiliary JSON files that are still maintained as stable exported references under `public/`, `parse_full` now synchronizes only the subset actually needed by the current runtime:

- `original_creatures_runtime.json`
- `original_doors_runtime.json`

And for support assets consumed from `src/assets/`:

- `original_wall_overlay_positions.json`

Other `original_*.json` files remain valuable as extraction/reference artifacts, but are no longer treated as part of the runtime package unless the app actually consumes them.

Current extraction-side reference sync:

- `assets/OriginalDataExtraction/output/original_level_content.json`

For wall overlays specifically:

- `public/original_wall_overlay_positions.json` remains the full extracted/reference export
- `assets/OriginalDataExtraction/output/runtime_wall_overlay_positions.json` is the compact runtime snapshot
- `src/assets/original_wall_overlay_positions.json` is the canonical runtime copy of that compact snapshot

Current runtime package target:

- `src/assets/data/dungeon.json`
- `src/assets/data/game_db.json`
- `src/assets/data/original_creatures_runtime.json`
- `src/assets/data/original_doors_runtime.json`
- `src/assets/data/runtime_data_manifest.json`
- `src/assets/original_wall_overlay_positions.json`

`mechanisms.json` is still generated by the pipeline as a useful extracted reference artifact, but it is no longer part of the runtime-required set for the app as currently wired.

## Why this is cleaner

- one canonical runtime location
- less silent divergence risk between `public/` and `src/assets/data/`
- parser behavior now matches the current app architecture
- easier future optimization around data loading and chunking
- the runtime no longer ships the full extraction/audit dump when it only needs a compact gameplay snapshot
- the runtime no longer ships the full wall-overlay reference export when it only needs `fixedFaces`

## Notes

- `public/` still exists for browser-served static assets and other exported references that are not part of this specific runtime canonical pair.
- In the cleaned layout, `public/` is now mostly:
  - browser-served asset folders
  - `graphics_*.json` extraction inputs
  - `original_creatures_runtime.json`
  - `original_doors_runtime.json`
  - `original_wall_overlay_positions.json`
  - `vite.svg`
- Some older comments or audit scripts may still mention `public/dungeon.json` or `public/game_db.json`; those should be considered legacy references and updated progressively when touched.
- `runtime_data_manifest.json` is intended as the quick source-of-truth summary for "what the parser packaged for runtime" during future cleanup work.
- If a few older JSON files remain physically present in `src/assets/data/` after a transition, the manifest should be treated as authoritative over directory leftovers.
- `docs/PUBLIC_DIRECTORY_AUDIT.md` tracks the remaining role of files under `public/` so runtime cleanup and pipeline cleanup do not get mixed together.
